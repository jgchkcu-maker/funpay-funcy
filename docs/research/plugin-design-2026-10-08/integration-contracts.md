## Контракты, которые должны согласовать агенты

1. **Контекст аккаунта:** accountId — подтверждённый ID продавца FunPay; операции и настройки привязаны к нему. Контекст сессии включает generation/epoch. Смена cookie останавливает выдачу и инвалидирует auth/order caches. Автоматизация MVP работает для одного активного аккаунта. Во время неё живые снимки других аккаунтов через подмену общей cookie выключены; показываются кэшированные данные. Общее обещание мультилогина не следует из наличия нескольких записанных golden_key.

2. **Проверенный заказ:** уведомление чата служит сигналом перечитать заказ. До закупки/резерва подтверждаются продавец, статус, привязка к точному лоту, количество, покупатель и чат. Неизвестное обязательное поле не заменяется удобным значением. Нужны отдельные evidence/source и timestamp снимка. Уже подтверждённые к выдаче заказы восстанавливаются независимо от повторного chat preview.

3. **Владелец выполнения:** один dispatcher выбирает ровно один источник выдачи для заказа: существующие товары FunPay, текстовый шаблон, локальный склад или поставщик. Автозакупка не становится вторым параллельным обработчиком поверх текущей выдачи.

4. **Деньги:** decimal string + currency + назначение/допустимая точность. Цена единицы лота, сумма платежа и фактическое поступление не обязаны иметь одинаковую точность. Расчёт прибыли начинается с поступления продавцу; комиссия покупателя не вычитается повторно. Нет вычисленной прибыли при неизвестной себестоимости/FX.

5. **Резерв:** применимые ресурсы и запись попытки резервируются одной локальной транзакцией. Для локального склада это конкретные единицы, для поставщика — бюджет; резервировать несуществующие локальные товары для supplier-источника не нужно. Неизвестный исход закупки/выдачи удерживает соответствующий резерв. Повторный charge требует установленного исхода предыдущего. Отмена заказа FunPay не доказывает отмену закупки поставщика.

6. **Идемпотентность:** стабильный внутренний ключ попытки и provider reference сохраняются до side effect. Наличие request/reference в API само по себе не доказывает server-side дедупликацию. Без подтверждённой дедупликации/поиска неоднозначный исход уходит на сверку и ручное решение. Tombstones закупок не удаляются общей очисткой операций так, чтобы старый заказ мог снова списать деньги.

7. **Активность лота:** ручной intent + причины блокировки (расписание, подтверждённое отсутствие товара, бюджет, цена, ошибка конфигурации). Причины объединяет один решатель; каждый модуль управляет только своей причиной. Снятие одной причины не снимает остальные. Лот, уже выключенный при подключении автоматизации, не принимается как выключенный ею: включение требует явного opt-in и сохранённого происхождения управления. По одному boolean невозможно увидеть ручное «выключить» уже выключенного лота, поэтому нужен явный постоянный запрет «Не включать автоматически». Неизвестный статус удалённого наличия — отдельное состояние со свежестью, не ноль и не доказательство наличия.

8. **Запись лота:** одна очередь на accountId + offerId для полной формы; автоматическое поле price принадлежит одной политике. Новый запрос читает актуальную форму внутри очереди. Fingerprint/expect и post-read уменьшают риск, но не являются server-side CAS против действий продавца в самом сайте.

9. **Секреты:** background vault на extension origin, redacted DTO для content UI. Маскирование поля и запрет экспорта — отдельные меры, не изоляция доступа. Глобальная настройка TRUSTED_CONTEXTS для существующего chrome.storage.local сломает content-script настройки и требует отдельного обоснования. Агент поставщиков должен выбрать конкретный способ ввода и хранения ключа.

10. **UI:** расширять существующие страницы. Отдельные новые страницы допустимы только для самостоятельной задачи; «Операции» в финансах означают денежные операции, их нельзя незаметно смешать с журналом попыток выдачи. Секреты, внутренние статусы и raw ответы API не выводятся в обычные финансовые выгрузки.

11. **Восстановление:** alarm — сигнал проверить сохранённые dueAt и состояния, а не единственный источник расписания. При старте/пробуждении пересчитывается желаемое текущее состояние. Просроченные напоминания не отправляются пачкой. Сервер нужен при требовании непрерывной работы вне запущенного Chrome или под специфические ограничения поставщика.

12. **Границы причин остановки:** закрытое окно расписания запрещает новые продажи, но не отменяет обязательства уже оплаченного заказа и не останавливает его первую закупку само по себе. Проблема конкретного заказа/замены — отдельный order hold с владельцем и revision. Напоминание об отзыве требует подтверждённой выдачи и свежего подтверждения завершения FunPay; проблема, возврат, замена, неизвестная выдача или любой существующий отзыв отменяют его. Исправление проблемы не запускает прежнее напоминание автоматически.

13. **Минимальная история:** добавить неизменяемые attempts/events для закупки и выдачи, сохранив текущую запись как проекцию состояния. Полный event sourcing всех настроек и UI для этого не требуется. Секретный результат хранится отдельно от безопасной истории; обычная карточка заказа получает метаданные и разрешённые действия.
