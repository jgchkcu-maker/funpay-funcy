- `background/lot_writer.js:22`: toFixed(2) считает 0.003 и 0.004 одинаковыми. patchLot читает и отправляет полную форму без общей очереди. expect не является server-side CAS.
- `background/lot_availability.js:22`: положительный productCount включает любой неактивный лот; нет происхождения выключения, ручного запрета, freshness или расписания.
- `background/order_details.js:57`: неизвестное количество превращается в 1; совпадение текущего названия может разрешить lot binding. Финальный ревьювер дополнительно подтвердил offscreen.js:1162–1164: prefix regex/parseInt принимают 1,5/1.5 как1, 2abc как2. Проверять нужно исходное quantity целиком с unit.
- `background/autoresponder.js`: verifyIAmSeller допускает обработку при ошибке; handleAutoDelivery не требует paid. sendChatMessage повторяет POST через fetchWithRetry; malformed 2xx может считаться успехом. reconcile читает первую страницу и пропускает известные заказы, даже невыданные.

## Предлагаемые общие правила для ревью

1. MVP автоматизации — один подтверждённый активный FunPay-аккаунт. AccountId и session epoch входят в операции/кэши/настройки; смена сессии останавливает эффекты и инвалидирует кэши. Живые снимки чужих аккаунтов через общую cookie при автоматизации выключены. Это не обещание изоляции всех вкладок одним mutex.
2. Чат — сигнал перечитать заказ. До расходов подтверждаются seller/currentAccount, paid, orderId, точный offer, quantity, buyer/chat и обязательные поля SKU. Неизвестное поле блокирует, а не получает fallback. Legacy-записи без подтверждённого аккаунта не replay автоматически.
3. Один fulfillment dispatcher закрепляет один источник заказа: товары FunPay, шаблон, local pool или supplier. Покупка и выдача — отдельные состояния. Повтор выдачи не покупает товар заново.
4. Деньги — decimal string + currency + precision/quantum по назначению, не универсальные копейки. Прибыль начинается с поступления продавцу; неизвестные cost/FX остаются неизвестными. Фактические затраты заказа — отдельный immutable ledger с allocations/корректировками, legacy cost snapshot — оценка.
5. Применимые ресурсы резервируются вместе с записью попытки в одной локальной транзакции: конкретные единицы для local pool, бюджет для supplier. Не резервировать несуществующие local units для supplier. Uncertain/partial не освобождаются по TTL; refund FunPay не отменяет закупку и не возвращает раскрытый код на склад.
6. Reference/body hash сохраняются до POST. Reference не доказывает серверную идемпотентность. Lookup: found/proven_absent/inconclusive/unsupported. Таймаут не разрешает повторную покупку. Purchase tombstones живут дольше общей очистки журнала. Свежий GET quote не является cap на следующее списание.
7. Один resolver объединяет manualIntent и blockers stock/schedule/budget/price/configuration. Каждый модуль снимает только свою причину. Уже неактивный при подключении лот не считается выключенным автоматизацией. Нужны opt-in и постоянный запрет «Не включать автоматически»: boolean не позволяет обнаружить ручное выключение уже выключенного лота.
8. Все изменения существующего лота идут через очередь accountId+offerId и свежую полную форму внутри очереди. UI передаёт намеренные поля/операции, не старую полную форму. Price имеет одного владельца. Удаление существующего offer сериализовано и ставит terminal guard; создание offer_id=0 отдельно. Fingerprint/expect/post-read снижают риск гонки с сайтом, но не дают серверного CAS.
9. Supplier keys вводятся на доверенной extension-странице и хранятся в отдельном extension-origin IndexedDB vault. Content UI получает redacted DTO. Не переключать весь storage.local на TRUSTED_CONTEXTS без миграции существующих страниц; не экспортировать результаты выдачи/headers/raw API.
10. Reuse UI: цены/расписания в «Управлении лотами»; склад в «Автовыдаче»; напоминания в «Отзывы и бонусы»; actual cost в «Финансах»; новая «Поставщики» внутри «Лоты и продажи». Журнал «Заказы и выдачи» предварительно — вкладка Автовыдачи, не финансовые «Операции».
11. Alarm — сигнал проверить persisted dueAt/state; восстановление при старте/пробуждении, без проигрывания старых переключений или пачек напоминаний. Закрытый Chrome не даёт SLA 24/7. Сервер — отдельный этап только при таком требовании/ограничении API.
12. ScheduleClosed запрещает новые продажи, но не отменяет paid-обязательство и само по себе не запрещает первую закупку уже оплаченного заказа. Order hold имеет отдельный owner/revision. Reminder требует verified fulfillmentCompletedAt и свежего завершения FunPay; отзыв/проблема/замена/refund/uncertain отменяет задачу, исправление проблемы не возобновляет её автоматически.
13. Не нужен полный event sourcing приложения. Достаточны immutable attempts/events закупки/выдачи и текущая проекция состояния. UI получает допустимые действия по evidence/capabilities.

## Что обязан решить финальный ревьювер

Достаточное доказательство offer binding без прямой ссылки; миграция старой дедупликации; минимальный объём foundation; подходящее место общей очереди; реальные блокеры unattended закупки; границы наблюдения ручных действий; точность/quantity/settlement по категориям; риски завышенных обещаний готовых Cardinal-плагинов.

Дополнительная независимая проверка координатора: finance_data.aggregateProfit:1545 сейчас фасад, который для массива синхронно вызывает engine.calculateProfitAggregates. Поэтому предложение «соединять cost в aggregateProfit» требует уточнения: background должен отдавать безопасную проекцию actualCost, а enrichment выполняется до существующего синхронного расчёта либо в явном новом async API. Нельзя незаметно сделать все вызовы Promise и сломать графики.

FunPay order-secrets-box описан в самом offscreen parser как уже выданные товары. Источник funpay_secrets — evidence/опциональная отправка копии товара конкретного заказа, а не свободный локальный склад. Он не требует новой закупки/резерва кода и не доказывает, что именно наше сообщение дошло.
