# Поставщики и автозакупка: архитектурное решение

Проверено 8 октября 2026 года. Прочитаны исследование поставщиков, дорожная карта и текущий код; применимых `AGENTS.md` не найдено. Runtime-код не изменялся, ключи не запрашивались, реальные покупки не выполнялись. Ниже «подтверждено» означает публичный официальный контракт/код, а не успешный запрос с партнёрским аккаунтом.

## Решение и границы первого выпуска

Первым выбирать **AppRoute**, начиная с каталога, баланса, ручной привязки одного voucher SKU и контролируемой закупки по проверенному заказу. Автоматический режим включать отдельным этапом после доказательства идентификации заказа, финансового журнала и восстановления. DesslyHub — следующий кандидат для конкретной категории; NS.Gifts — кандидат после получения официального партнёрского контракта. Наличие API не подтверждает наличие нужной подписки, условия перепродажи, минимальный депозит или прибыльность.

Общий интерфейс из прежнего плана `createOrder(customId)/getStatus(customId)` слишком оптимистичен: API могут принимать reference, но искать только внешний transaction ID; отсутствие результата поиска может означать задержку индексации. Правило «не найдено → повторить create» пока запрещено. Браузерный модуль восстанавливается после запуска Chrome, но не обеспечивает непрерывное выполнение при завершённом Chrome, сне компьютера или потере сети.

## Что установлено по API

**AppRoute.** Официальный README задаёт `https://approute.ru/api/v1` для российских клиентов, `.io` для международных, авторизацию `X-API-Key`, получение ключа в соответствующем dashboard. Изменение мая 2026 различает rate limit `429` и лимит расходов ключа `409 API_KEY_LIMIT_EXCEEDED`; активный ключ не обязательно допускает новую покупку. [Официальный README](https://github.com/AppRoute-FZCO/AppRoute-Public-API-SDK).

Подтверждённые операции: `GET /services`, `/services/{serviceId}`, `/services/{serviceId}/stock`, `/services/{serviceId}/items/{itemId}`; `POST /services/items/lookup` принимает до 100 пар. Это чтение каталога, а не резерв товара. [ServicesResource](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/resources/services.ts).

Покупка — `POST /orders`, параметры включают `ordersType`, `itemId`, `quantity`, `fields`, `referenceId`/`reference`; проверка DTU использует `checkOnly:true`. История — `GET /orders?referenceId=…` либо `orderId=…`, с `limit/offset`. Voucher-пилоту нужны `ordersType:shop`, конкретный item, целое количество и заранее сохранённый reference. Для сверки сопоставлять SKU, количество, аккаунт поставщика и результат, проходить все страницы. [OrdersResource](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/resources/orders.ts), [модели результата](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/models/orders.ts).

`GET /accounts` и `/accounts/transactions` подтверждены YAML; баланс описан как USDT. YAML прямо предупреждает о неполном покрытии orders/services; встречается `transactionUUID`, тогда как TS-модель использует `transactionUuid`, и различается обязательность reference. Необходимо зафиксировать реальные обезличенные ответы и точность сумм. [OpenAPI](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/openapi.yaml).

Transport распознаёт `IDEMPOTENCY_REPLAY`, но также повторяет **любой** метод при `429/500/502/503/504`. Это признак поддержки повторов, не описание её гарантии. Для расходного POST отключить retries; отдельно получить область уникальности reference, срок хранения, поведение одинакового ключа с другим body, конкурентного POST и отрицательного поиска. Без этого таймаут/5xx означает `uncertain`, а не повтор. [HttpTransport](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/transport/http-transport.ts).

**DesslyHub.** Официальная документация v2.0.3 требует заголовок `apikey` и обязательную проверку состояния после заявки. Подтверждены Steam Gift `POST https://desslyhub.com/api/v1/service/steamgift/sendgames` с `invite_url`, `package_id`, `region` и необязательным `reference`, а также `GET /api/v1/merchants/transaction/{transaction_id}/status`. В ответе ожидается transaction ID/pending. Reference не документирован как ключ идемпотентности; восстановление при потерянном ID остаётся блокером. На странице Gift есть противоречивый пример `status:success/error_code:-1`, поэтому адаптер не должен угадывать приоритет полей. [Введение](https://desslyhub.readme.io/reference/introduction), [Gift](https://desslyhub.readme.io/reference/post_apiv1steamgift), [Status](https://desslyhub.readme.io/reference/get_apiv1statustransaction_id). Категория ваучеров заявлена официально, но её endpoints здесь не проверены; не переносить на неё контракт Gift. [Ресурсы разработчика](https://github.com/DesslyHub/developer-resources).

**NS.Gifts.** Официальный сайт подтверждает B2B, gift cards/wallet/top-up и API заказов/статусов/выдачи. `https://api.ns.gifts/docs` вернул через исследовательский инструмент 502; авторизация, актуальная версия, custom ID, IP whitelist и endpoints **не подтверждены первичным источником**. Неофициальный клиент и Cardinal-плагин не заменяют договор API. До получения документации адаптер не планировать как готовый. [Официальный сайт](https://ns.gifts/).

## Почему текущий заказ нельзя автоматически оплачивать

Нужен отдельный `verifyPurchaseEligibility`, работающий с **свежей** страницей: подтверждённые currentAccountId/sellerId, orderId, buyerId/chatId, `status=paid`, доказанный offerId и категория, явное положительное целое количество, полный набор полей конкретного SKU. Возврат, неизвестное поле, расхождение участников, неоднозначный лот или смена аккаунта переводят заказ в `seller_action_required`.

Совпадение названия показывает кандидата продавцу, но не разрешает расходы. Синтетическая [фикстура](C:/Users/Usser/Desktop/funpay-funcy/tests/fixtures/order_page_paid.html) не доказывает действующий контракт FunPay.

## Контракты и восстановление

Предлагаемые локальные модули: `supplier_registry`, `suppliers/approute`, `supplier_orders`, `supplier_vault`. Адаптер предоставляет `capabilities`, `listCatalog`, `getOffer`, `getBalance`, `validateFields`, `quote`, `submit`, `lookupByReference`, `getOrder`, `getResult`. Неподдерживаемый поиск возвращает `unsupported`; результат сверки — `found | proven_absent | inconclusive`. `submit` возвращает `accepted | rejected_before_purchase | uncertain`; HTTP-код сам по себе не доказывает отсутствие списания. Capabilities отдельно описывают валюты, precision, quantityUnit, идемпотентность, polling, частичное выполнение и полноту выдачи.

Ключи данных: `(funpayAccountId, orderId)`, `(providerId, providerAccountId, procurementId)`; reference неизменяем и связан с hash body, revision привязки и попыткой. В одной транзакции сохранять резерв и попытку **до** сети. Текущий [ops_db:119](C:/Users/Usser/Desktop/funpay-funcy/background/ops_db.js:119) выполняет транзакции одного store; этого недостаточно для атомарного резерва бюджета вместе с закупкой. [beginOp:220](C:/Users/Usser/Desktop/funpay-funcy/background/ops_db.js:220) полезен для дедупликации, но доменный автомат закупки должен существовать отдельно: `validated → reserved → submitting → accepted/polling → fulfilled`, плюс `uncertain`, `rejected`, `partial`, `seller_action_required`. Выдача имеет отдельный журнал и итог.

Quote хранит SKU/вариант, количество и единицу, decimal string `amount`, валюту расчёта, валюту списания, комиссии, `observedAt/validUntil`, evidence. Арифметика — decimal либо целое с явной шкалой; универсальные копейки непригодны для USDT. FX сохранять с источником/временем, неизвестный курс блокирует закупку. `quantity = confirmedFunPayQty × mappedQtyPerUnit`; дробные количества разрешать только явно поддерживающим API. ActualCost неизменяем на уровне заказа, включая комиссии, частичное исполнение и возвраты; не перезаписывать себестоимость лота задним числом.

Свежая цена не фиксирует сумму последующего POST: в проверенных параметрах AppRoute нет доказанного `maxPrice`/locked quote ID. `amount` для пополнения не считать пределом списания. Строгий maximum cost требует серверного ограничения поставщика; без него возможен только явно согласованный пилот с ограниченным риском, а unattended остаётся заблокированным. Существующий [createSnapshot:258](C:/Users/Usser/Desktop/funpay-funcy/content/features/cost_basis_store.js:258) хранит число по лоту и не заменяет журнал фактических затрат закупки.

Резерв ограничивается свежим доступным балансом, минус незавершённые/uncertain закупки, лимитами на заказ/день и headroom ключа. Общий кошелёк поставщика резервируется по providerAccountId+currency даже для разных FunPay-аккаунтов. Устаревший quote/баланс требует сверки; TTL не освобождает uncertain. Переключение — только между вручную подтверждёнными эквивалентами (регион, номинал, срок, активация), после доказанного отказа без покупки либо подтверждённого возврата. Частичное исполнение не разрешает повтор всего количества.

[orders:23](C:/Users/Usser/Desktop/funpay-funcy/background/ops_db.js:23), кэши loader и `reconcileSeededAt` сегодня глобальны. [fptSnapshotForKey:1164](C:/Users/Usser/Desktop/funpay-funcy/background/background.js:1164) сериализует только снимки и временно меняет глобальную cookie; [setGoldenKey:2051](C:/Users/Usser/Desktop/funpay-funcy/background/background.js:2051) и движок идут отдельно. Нужны единый session gate/epoch, сброс кэшей, повторная проверка аккаунта перед выдачей. Закупки со сменившейся сессией приостанавливать. [prune:288](C:/Users/Usser/Desktop/funpay-funcy/background/ops_db.js:288) удаляет старые завершённые записи: для закупок сохранять компактный постоянный tombstone, иначе старый replay вновь потратит деньги.

**Один dispatcher** назначает заказу ровно один источник: товары FunPay, шаблон, склад или поставщик; закупка не запускается параллельной веткой возле старой выдачи. Legacy-заказы без доказанного аккаунта мигрируют в карантин без расходного replay. Отмена FunPay не доказывает отмену поставщика; уже купленный результат сохраняется для решения продавца.

Перед выдачей нужен новый strict send policy: [fetchWithRetry:25](C:/Users/Usser/Desktop/funpay-funcy/background/autoresponder.js:25) повторяет POST, используемый [sendChatMessage:150](C:/Users/Usser/Desktop/funpay-funcy/background/autoresponder.js:150), а malformed 2xx превращается в успех. Журнал вокруг вызова этого не исправляет. Сохранять stable partId/hash и receipt каждой части, проверять доказанное подтверждение runner; неизвестный ответ означает uncertain без повтора. Сверка истории чата ищет конкретную часть, а не общий невидимый маркер. Сбой выдачи никогда не запускает повторную закупку.

## Браузер, секреты и интерфейс

Фоновые запросы с host permission технически поддерживаются Chrome; это не доказывает, что поставщик допускает browser-origin, динамический IP или локальное хранение ключа. Добавлять optional permissions только известных `.ru/.io` origins, запрос — при подключении; проверять отказ/отзыв разрешения. Не нужен произвольный URL. Требования server-only, стабильного IP, webhook или SLA означают отдельный серверный проект. [Сеть Chrome](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests), [жизненный цикл](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).

Не переключать весь storage.local в TRUSTED_CONTEXTS без миграции существующих страниц. Не экспортировать коды выдачи, auth headers и полные ответы; журнал содержит безопасные метаданные, traceId, hash/evidenceRef.
