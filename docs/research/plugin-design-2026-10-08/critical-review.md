# Независимое критическое ревью шести модулей

Дата: 2026-10-08. Проверены текущий код, шесть отчётов, integration-contracts.md и implementation-plan.md. Ревьювер не автор этих материалов. Runtime, настройки, аккаунты, заказы и Git не изменялись; создана только эта записка. Общий вердикт: направление пригодно для последовательной реализации, но текущая основа не разрешает безопасную автозакупку. Значительная часть прежних опасных рекомендаций уже исправлена; ниже отделены реальные дефекты от выбранных ограничений продукта.

**1. Поставщики — принять один контролируемый пилот, отклонить обещание готовой unattended-интеграции.** AppRoute обоснован как первый исследуемый адаптер, но доступность каталога, нужного SKU, браузерного origin и конкретного партнёрского тарифа ещё предстоит проверить. Reference и код IDEMPOTENCY_REPLAY не устанавливают scope, TTL, конкурентное поведение и достаточность отрицательного поиска. Пустая страница GET не разрешает новую покупку. [Orders SDK](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/resources/orders.ts) подтверждает методы и параметры, а не все эти гарантии.

Отчёт supplier-autopurchase.md:11 нужно дополнить: [официальный README](https://github.com/AppRoute-FZCO/AppRoute-Public-API-SDK) действительно описывает накопительный transactionLimit, transactionUsed и остаток ключа, с отказом 409. Это полезный серверный предел общего расхода; он не фиксирует цену отдельного заказа. Отсутствие maxPrice в просмотренном SDK означает неизвестность, а не доказанное отсутствие во всём API. Возможен пилот с отдельным небольшим лимитом ключа и явно выбранным ценовым риском; гарантированную маржу он не обеспечивает. Универсальные customId/getStatus отклонить: у DesslyHub проверка привязана к transaction_id, потерянный ID и reference recovery пока не решены. [Gift](https://desslyhub.readme.io/reference/post_apiv1steamgift), [Status](https://desslyhub.readme.io/reference/get_apiv1statustransaction_id). Недоступность NS.Gifts docs исследовательскому инструменту не доказывает непригодность сервиса. Ключ в fpToolsSecrets с запретом экспорта недостаточен: `popup_actions.js:68` читает весь storage.local. Поддержать предложенные доверенный extension-ввод, отдельный extension-origin vault и узкие redacted DTO.

**2. Автоцены и прибыль — принять расчёт и ручной preview, автоматическую запись отложить.** Идея floor правильна, слепой демпинг опасен из-за разных комплектов, регионов, единиц и buyer totals. Нужно исправить фактическую двусмысленность pricing-profit.md:17: `finance_data.js:1545–1562` сейчас ничего не соединяет с actualCost; для массива это синхронный вызов чистого движка. Background должен отдавать безопасную проекцию затрат, enrichment выполняется заранее либо через явно новый async API. Незаметный Promise нарушит существующий контракт, даже если один текущий потребитель использует await.

`cost_basis_store.js:258` сохраняет стоимость оффера, без количества; `sales_db.js:185` удерживает первый snapshot; `profit_engine.js:127–149` трактует его как полную стоимость заказа. Такой snapshot годится только как явно названная оценка. Закупка требует отдельного фактического ledger, распределения стоимости партии с остатком округления, replacement/provider-refund corrections и исторического FX. Возврат выручки не уничтожает расходы: нынешнее исключение refunded на `profit_engine.js:120–122` скроет убыток. [FunPay подтверждает](https://funpay.freshdesk.com/support/solutions/articles/103000273187-%D0%BA%D0%BE%D0%BC%D0%B8%D1%81%D1%81%D0%B8%D0%B8), что продавец получает указанную им сумму; комиссию покупателя второй раз не вычитать.

**3. Остатки — принять разделение источников, не делать LocalPool обязательной основой supplier-пилота.** `auto_delivery_store.js:80–124` считает содержимое формы удалённого склада FunPay; при ошибке прежний count сохраняется без срока достоверности. Это не наш резервируемый local stock. Ещё существеннее: `offscreen.js:1143–1145` читает order-secrets-box как уже выданный товар конкретного заказа. Повторно закупать его или помещать в свободный пул нельзя; отправка копии в чат — самостоятельная настройка после проверки buyer-visible поведения.

`lot_availability.js:22/38` включает inactive при положительном count, не проверяя происхождение выключения, freshness и config.enabled. Нужны явное принятие управления, постоянный manual-off и причины остановки, принадлежащие отдельным модулям. Boolean не обнаруживает ручную команду off уже выключенному лоту. finite, unknown и unbounded различаются; отсутствие quantity не означает бесконечность. Даже свежий supplier snapshot не резервирует внешний товар. FIFO local units и их атомарный резерв нужны только при реально выбранном local source.

**4. Напоминания — принять один нейтральный запрос, пересмотреть цену ограничения scope.** Рекомендация только для новых управляемых цифровых выдач уменьшает неопределённость, но исключает ручных продавцов и услуги. Это продуктовый выбор, не обязательный закон архитектуры. Будущая поддержка ручных заказов может начинаться с подтверждения продавцом конкретного исполнения с order-bound evidence, отдельно помеченного как ручное; весь supplier ledger для этого не нужен. Нельзя незаметно приравнять такую отметку к серверному доказательству.

`parseOrderPageForReview` возвращает null и при отсутствии звёзд, и при собственном отзыве, и при ошибке (`offscreen.js:980–1007`). Нужен present/absent/unknown на распознанной странице. Любой отзыв отменяет запрос. EnabledFrom, baseline, атомарный лимит на чат и durable send нужны до отправки; исправление старых бонусов не должно блокировать read-only preview. [ago106](https://raw.githubusercontent.com/ago106/fpc-plugins/main/review_reminder.py):153–170/457–508 пропускает низкие оценки, допускает немедленную первую отправку и повторный append CLOSED. Переносить это поведение нельзя.

**5. Проблемные заказы — принять раздельные закупку, результат и выдачу, сократить стартовую схему.** Карточка и read-only сверка полезны раньше полного dispatcher. Проекция плюс неизменяемые записи реально совершённых попыток достаточны; каталог событий всего приложения и универсальная машина workflow избыточны. Однако карточка не должна предлагать «Повторить» без знания, какой эффект повторяется. Повтор отправки использует прежний результат; замена — отдельное разрешение нового расхода. Refund покупателю не означает supplier refund и не освобождает раскрытый код.

`autoresponder.js:773–790` просматривает первую страницу и пропускает известные невыданные заказы; журнал не является рабочей очередью исполнения. Нужны persisted known-unfulfilled плюс пагинация, а не один watermark. `ops_db.js:288–304` очищает старые done/failed: purchase tombstones должны переживать такую очистку, пока возможен replay. Partial и late result сохраняются даже после hold/refund. TTL сам по себе не доказывает, что списания или выдачи не было.

**6. Расписания — принять небольшой модуль на существующей странице лотов.** Weekly windows, фиксированная зона аккаунта, preview и пересчёт состояния сейчас достаточны; RRULE framework, holidays и сервер для MVP не обоснованы. DST-политика должна быть показана в preview и проверена gap/fold fixtures. Persisted dueAt не делает alarm точным: [Chrome допускает произвольную задержку](https://developer.chrome.com/docs/extensions/reference/api/alarms), а устройство он не будит. `job_scheduler.js:36–38` также не возвращает Promise создания alarm. Проверка при старте worker обязательна независимо от heartbeat автоответчика. После сна применять текущее состояние, не проигрывать пропущенные открытия. ScheduleClosed ограничивает новые продажи; уже оплаченный заказ сохраняет обязательство исполнения.

**P0 — блокеры денежных и выдающих эффектов.**

- Проверка роли допускает ошибки и неизвестность (`autoresponder.js:445–459`), выдача не требует paid (`:632–660`), event chat имеет приоритет над buyerChat (`:636`). Loader сам подставляет запрошенный orderId и quantity=1 (`order_details.js:54–57`); название не является историческим offer binding. Нужен fresh verifier страницы, роли, статуса, order/offer/buyer/chat и исходного количества. Независимо найден дополнительный дефект: `offscreen.js:1162–1164` через начальные цифры и parseInt превращает `1,5`, `1.5` в 1, `2abc` в 2. Проверять только полученный integer поздно: разбирать исходное значение целиком вместе с unit по контракту категории.
- `sendChatMessage` повторяет POST через retry (`autoresponder.js:25–53/150`), а нечитаемый 2xx становится успехом (`:162–164`). Журнал до вызова не предотвращает дубли внутри этого вызова. До эффекта — durable attempt; далее один POST и проверенный acknowledgment/read-back. Timeout, malformed response и прерванный sending — uncertain. Отсутствие сообщения в неполной истории не разрешает повтор. Fallback выдачи без журнала (`:593`) для нового пути закрыть. SDK AppRoute также [повторяет 429/5xx независимо от метода](https://raw.githubusercontent.com/AppRoute-FZCO/AppRoute-Public-API-SDK/main/javascript/src/transport/http-transport.ts); готовый transport нельзя копировать без изменения политики расходных запросов.
- `background.js:1164–1234` подменяет общую cookie и затем восстанавливает старую; `setGoldenKey:2051` вне этой цепочки. Один mutex snapshots не изолирует вкладки и может вернуть предыдущую сессию после нового входа. MVP — один подтверждённый аккаунт, отключённые чужие live snapshots, account/epoch-bound кэши и остановка новых эффектов при смене сессии. Даже это не обещает атомарной защиты от ручного login между последним GET и POST.

**P1 — запись лотов и точность; P2 — избыточные обещания.**

Очередь нужна вокруг намерения и свежего read–mutate–save, не только POST. `bulk_lot_editor.js:104–152` передаёт полную устаревающую форму; `saveSingleLot:1892` даже не перечитывает её при наличии fields, а `:1909` допускает partial fallback. Последовательная отправка stale active снова откроет закрытый лот. В миграцию входят `lot_management.js:708/834/936`, `inline_price_editor.js:190`, background saveSingleLot и deletion paths `background.js:1848–1859`, `profile_descriptions.js:228–233`. Delete требует terminal guard против queued updates. Создание offer_id=0 (`lot_cloning.js:1015`, background cloneCreateLot:1787/import:1106, verification lot:201) — отдельный поток с контролем неопределённого исхода; не приписывать ему очередь исходного offer. В частности, import:1135–1144 и cloneCreateLot:1795 сейчас повторяют создание после неопределённых ошибок. Expect/post-read не дают серверного CAS.

`lot_writer.js:22` считает 0.003 и 0.004 одинаковыми. Чистый repro на текущем модуле: status=unchanged, saves=0, conflicts=[]; парсер количества дал описанное усечение. Нужны decimal/quantum по назначению, отдельные unknown/known-zero, валюта и единица. Универсальные «копейки» для всех категорий отклонить. P2: три API сразу, public repo как разрешение переноса, универсальный getStatus, обещание заработка с 200–400 рублей — неподтверждённые советы. Проверять лицензию конкретного кода, ассортимент, комиссии, депозит, спрос и оборот; публичность репозитория этого не заменяет.

**Минимальный вертикальный выпуск и допуск эффектов.** Сначала независимые каталог/ручной mapping, pricing и schedule preview, read-only карточка: без расходов, сообщений и публикации. Затем отдельный выпуск публикации: общая очередь, account guard, manual ownership/resolver и weekly schedule; supplier ledger для него не нужен.

Для первого денежного среза выбрать один AppRoute voucher SKU, целые units, один аккаунт и один заказ одновременно, кнопку подтверждения закупки и отдельное ручное раскрытие сохранённого результата. Нужны узкая атомарная запись claim/reservation/attempt, фактическая стоимость, устойчивый reference, recovery uncertain и реальный общий cap ключа; local pools и второй адаптер отложить. Автовыдача включается после проверенного sender/receipts, unattended закупка — после установленных recovery/idempotency capabilities. Отсутствие per-order cap допускает только отдельно выбранный ценовой риск с подтверждённым общим cap; это не отменяет остальные проверки. Проверить duplicate/crash/partial/account switch, последнюю единицу бюджета, raw quantity, stale bulk/delete, refund с retained cost. Текущие 19/19 базовых тестов, повторённые координатором, не проверяют новые гарантии; весь набор заново не запускался. Live HTML, партнёрские ответы и реальные списания этим ревью не подтверждены.
