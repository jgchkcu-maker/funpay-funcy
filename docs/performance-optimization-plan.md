# План оптимизации FunPay Funcy (ред. 3)

## Контекст

Расширение заметно тормозит на страницах FunPay. План проверяет три предполагаемых источника нагрузки:

1. **Объём подключаемого кода.** В текущем `content_scripts[2]` — 109 JS-файлов суммарно 2 647 789 байт и 8 CSS-файлов суммарно 755 806 байт. Значения проверены 10.10.2026 по рабочему дереву; ранние скрипты `document_start` в эти числа не включены. На новой странице код расширения запускается заново, но стоимость разбора может уменьшаться благодаря кешам браузера. Размер файлов сам по себе не доказывает источник лагов. Предварительная оценка части для попапа — около 1,2 МБ JS и 480 КБ CSS; окончательный состав и объём определяются после аудита зависимостей.
2. **Частые DOM-наблюдения.** Часть `MutationObserver` на `body`/`#content` повторяет поиск элементов, чтение `chrome.storage` и `getComputedStyle`. Таймеры заказов создают отдельные наблюдатели на каждую строку. Число наблюдателей и стоимость callback'ов фиксируются в Фазе 0.
3. **Работа скрытого интерфейса.** Анимации невидимых псевдоэлементов кнопки в шапке, содержимое закрытого попапа и ресурсы `cursor_fx`, созданные при выключенных эффектах. Фактические затраты подтверждаются trace.

**Цель:** снизить фоновую нагрузку и стоимость загрузки страниц, сохранив поведение функций. Внешний вид не должен меняться заметно для пользователя. Допустимые отличия перечисляются явно и сверяются визуально.

**Порядок фаз:** 0 → 2 → 1 → 3. Каждая фаза проверяется и откатывается отдельно. Коммиты содержат только изменения своей фазы; исходные изменения пользователя в них не включаются.

**Сохраняется:**

- Раннее применение темы: `theme_flash_fix.js`, `early_custom_styles.js`, `theme_buttons.js` при `document_start` и необходимые им зависимости.
- Рабочая логика автоответчика, автовыдачи и автоподнятия в background, включая `fpt_engine.js`, offscreen и watchdog. В Фазе 3 добавляется только обработчик загрузки UI-пакета.
- Функции на страницах и общие зависимости запускаются до открытия меню. Форматы настроек и способы их сохранения не меняются.
- Правила `CLAUDE.md` про `<select>`: `popup_components.js` и `page_selects.js` загружаются сразу.

## Фаза 1. Точечная оптимизация observer'ов

Общий DOM-наблюдатель не вводится. Каждая функция сохраняет текущий target и опции наблюдения, если исключение явно не описано ниже.

### Планировщик в `content/utils.js`

**`fptCoalesce(fn, { hiddenDelay = 100, records = false, name = fn.name || 'callback' } = {})`** возвращает планировщик с `cancel()` и `dispose()`.

- Для callback'ов, перечитывающих текущее состояние DOM, `records: false`: несколько вызовов объединяются в один запуск. Аргументы таких callback'ов не должны содержать данные, которые необходимо сохранить.
- Для callback'ов, читающих `MutationRecord`/`addedNodes`, обязательно `records: true`: массивы записей всех вызовов накапливаются в порядке поступления. При сбросе `fn(records, observer)` получает всю пачку, включая первые вызовы. Каждый observer использует отдельный планировщик.
- В видимой вкладке планируется один `requestAnimationFrame`, в скрытой — один `setTimeout(hiddenDelay)`. Задержка в фоне не гарантирована: браузер может ограничивать таймеры.
- На `visibilitychange` уже ожидающий rAF отменяется и заменяется таймером при скрытии; при возвращении ожидающий таймер заменяется rAF. Пачка сохраняется, старый callback не запускается повторно.
- Идентификатор расписания и текущая пачка очищаются **до** вызова `fn`: новые мутации во время выполнения образуют следующую пачку.
- Ловить синхронные исключения и отклонения возвращённого promise, логировать с именем функции. Сохранять существующие guards от параллельных асинхронных запусков; объединение вызовов само по себе не сериализует async-работу.
- `cancel()` отменяет ожидающий запуск и освобождает накопленные записи. `dispose()` дополнительно удаляет обработчик `visibilitychange` и запрещает новые вызовы. При завершении жизненного цикла функции отключается и её observer.
- Выполнять необходимую первичную обработку уже существующего DOM при инициализации. rAF используется для уменьшения повторной работы; отсутствие визуального мигания подтверждать проверкой, а не гарантировать только способом планирования.

### Навигация в `content/utils.js`

**`fptOnUrlChange(fn)`** возвращает отписку и не зависит от DOM-мутаций.

- Основной источник — проверенное в Фазе 0 событие Navigation API `currententrychange`; дополнительно `popstate` и `hashchange`.
- Если API отсутствует или проверка isolated world не пройдена — один общий `setInterval(700)` для всех подписчиков вместо отдельных опросов.
- Сравнивать `location.href`, уведомлять один раз на фактическое изменение URL, передавать старый и новый адрес. Каждый потребитель сохраняет свою прежнюю проверку: изменение pathname или изменение полного URL.
- Изолировать синхронные ошибки и promise rejection каждого подписчика. Удалять общий таймер и обработчики после последней отписки.
- Первичную инициализацию функции выполнять отдельно. Не требовать смены URL для первого запуска.

   - `{ "js": [...], "css": [...] }` — единый источник состава и порядка для background и тестов. Пути фиксированы расширением; список файлов не принимается из сообщения страницы.
4. **`manifest.json`.**
   - Добавить `"scripting"`, убрать только файлы пакета из соответствующего content script, добавить `menu_theme.js` и `popup_shared.css`.
   - Для привязки к документу использовать Chrome 106+ и явно зафиксировать минимальную поддерживаемую версию. В этой фазе не использовать fallback на `frameIds`, который ослабляет защиту от инъекции после перехода страницы.

### Background: протокол загрузки

Ветка `action: 'fptLoadPopupBundle'` в `background/background.js`:

- Проверить `sender.tab.id`, `sender.documentId` и допустимый адрес отправителя. Использовать `target: { tabId: sender.tab.id, documentIds: [sender.documentId] }` и `world: 'ISOLATED'` для JS. [Chrome InjectionTarget](https://developer.chrome.com/docs/extensions/reference/api/scripting#type-InjectionTarget).
- Сначала прочитать и проверить JSON-пакет, затем подключать CSS и JS. JSON кешируется без сохранения навсегда отклонённого promise.
- Для документа хранить состояние попытки: `requestId`, статус, начатые этапы, подтверждённые файлы и маркер готовности. Перед подключением пакета атомарно занять попытку в isolated world документа. Состояние в документе не теряется при перезапуске service worker; одна только Map в background недостаточна.
- Служебный bootstrap для этого состояния отделить от JS пакета. Повторный запрос к уже занятому документу не запускает пакет снова. При утрате выполнявшейся операции состояние остаётся неопределённым до подтверждённой готовности или перезагрузки.
- Порядок: `insertCSS`, затем JS по одному файлу по порядку. Отмечать начало этапа **до** вызова API; отдельно отмечать подтверждённое завершение.
- Проверять ожидаемые экспорты и необходимые регистрации после загрузки. Успех вызова API и выполнение последнего файла сами по себе не заменяют проверку готовности всего пакета.
- Ответ содержит `requestId`, `ok`, `status: 'ready' | 'failed-not-started' | 'failed-partial' | 'unknown'`, `stage`, `injectionAttempted`, `started` и `completed`, а при ошибке — `error`.
- `failed-not-started` разрешён только после завершения попытки, когда подтверждено, что подключение **CSS и JS пакета не начиналось**. Например, JSON не удалось прочитать до инъекции. `completed: []` не является доказательством этого статуса.
- Ошибка после начала подключения классифицируется как `failed-partial` или `unknown`. Файл мог изменить глобалы и зарегистрировать действия до исключения; список завершённых файлов не описывает все побочные эффекты.
- Не удалять CSS и не запускать пакет повторно автоматически после частичной попытки. Безопасное восстановление — перезагрузка страницы.
- Сохранить канал асинхронного ответа в соответствии с существующим `onMessage`-обработчиком. Изменения не затрагивают другие команды background.

### Content: состояния загрузки и открытия

`ensureFpToolsPopup()` использует состояния `idle`, `loading`, `ready`, `failed-not-started`, `failed-partial`, `unknown`.

- Перед первым запросом проверить валидированную готовность: `__fptPopupBundleLoaded`, ожидаемые экспорты и регистрации. Список проверок соответствует JSON-пакету. Последний `popup_bundle_ready.js` выставляет флаг только после этих проверок.
- Все входы (`#fpToolsButton`, `templates.js`, другие обнаруженные вызовы) используют одну функцию и одну активную попытку. Повторные клики во время загрузки не отправляют новое сообщение и не вызывают второе переключение открыто/закрыто после завершения. Один запрос открытия выполняется один раз.
- При загрузке: `aria-busy="true"`, курсор `progress`. При выходе из ожидания восстанавливаются прежние значения.
- **Таймаут 15 секунд ограничивает ожидание UI, но не отменяет инъекцию.** Состояние становится `unknown`, исходный promise и идентификатор попытки сохраняются. Не возвращать `idle`, не отправлять повторный `fptLoadPopupBundle` и не начинать ещё одну инъекцию.
- Если результат неизвестен, показать предложение перезагрузить страницу. Повторный клик может проверить готовность существующей попытки, но не создаёт новую.
- **Поздний результат** обрабатывается для того же `requestId`: после подтверждённой готовности перейти в `ready`. Меню не открывать неожиданно после уже показанного таймаута; следующий явный запрос пользователя открывает его без новой загрузки.
- **`failed-not-started` от той же завершённой попытки:** показать ошибку; следующая явная попытка допускается. Не повторять автоматически.
- **Исключение `sendMessage`, потеря ответа, инвалидированный контекст:** статус `unknown`, если нет достоверного терминального результата. Не делать вывод об отсутствии инъекции из отсутствующего ответа или пустого списка файлов.
- **`failed-partial`:** повторная загрузка запрещена. Уведомление предлагает кнопку «Перезагрузить» с `location.reload()`; автоматической перезагрузки нет.
- После `ready` сборка DOM попапа имеет отдельный promise `__fpPopupBuilding`. При её ошибке сбрасывать promise только после cleanup: вызвать disposers уже смонтированных страниц, отключить созданные observers, timers и listeners, удалить частичный DOM. Если полный cleanup не обеспечен, предложить перезагрузку вместо повторного монтажа.
- Ошибка сборки не сбрасывает готовность загруженного пакета и не запускает его JS повторно. Форматы и значения настроек не изменяются при восстановлении.

### Тесты Фазы 3

**Существующие тесты интерфейса:** загружать пакет из JSON после manifest-файлов; контрактные тесты проверяют объединение manifest и пакета. Тестам темы подключить `menu_theme.js`. Эти тесты проверяют интерфейс и явно не считаются проверкой реальной инъекции расширения.

**Новый `tests/popup_lazy_load_browser.test.js`:** пакет заранее не подключается. Мок runtime воспроизводит этапы loader'а и сохранение состояния, включая успешное/частичное исполнение и потерянные ответы.

1. Первый клик: одно сообщение, попап открыт.
2. Быстрые повторные клики: одна загрузка, один монтаж, попап остаётся открытым.
3. Достоверный `failed-not-started`: уведомление, следующая явная попытка успешна.
4. Частичное выполнение: нового сообщения нет, предлагается перезагрузка.
5. Ожидание истекло, исходная операция продолжается: состояние `unknown`, кнопка не залипла, повторный клик не запускает загрузку.
6. Поздний успех после таймаута: готовность восстановлена, нет спонтанного открытия; следующий клик открывает попап без повторного сообщения.
7. Потеря ответа после выполненного JS, включая `completed: []` или отсутствие ответа: повторная инъекция запрещена.
8. Ошибка внутри файла после побочного эффекта: готовность не объявляется, файл повторно не исполняется.
9. Ошибка монтажа: cleanup предотвращает дубли listeners/observers при разрешённой повторной сборке; пакет не загружается заново.
10. До первого клика отсутствует `.fp-tools-popup`, работают тематические окна и `<select>` на страницах. После открытия их оформление сохраняется.
11. Изменение темы и настроек автоответчика после открытия применяется прежним способом.

**Новый `tests/popup_bundle_background.test.js`:** проверить `documentIds`, валидацию отправителя, CSS перед JS, порядок JS, фиксацию начала/завершения, невозможность двух попыток в одном документе и неизвестное состояние после утраты операции. На N-м файле ошибка может оставить побочные эффекты самого N-го файла, даже если подтверждены только первые N−1.

**Реальное расширение:** дополнительно проверить loader с распакованным расширением. Переход на новую страницу во время загрузки не должен подключать оставшиеся файлы в новый документ. Моки runtime и добавление `<script>` в тестовую страницу не доказывают работу `chrome.scripting` в isolated world.

**Контракт:** каждый файл существует, отсутствует одновременно в manifest и пакете, JS сохраняет относительный порядок manifest. `menu_theme.js`, `popup_shared.css`, `popup_components.js` и `page_selects.js` загружаются сразу. Разрешение `scripting` и минимальная версия присутствуют.
