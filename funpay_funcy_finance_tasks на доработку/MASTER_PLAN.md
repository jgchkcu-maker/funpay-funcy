# MASTER PLAN — «Финансы»

## 1. Цель

Собрать разрозненную аналитику FunPay Funcy в один финансовый центр и добавить полноценную модель прибыли.

Сейчас проект уже содержит:
- статистику продаж;
- статистику покупок;
- статистику операций баланса;
- line charts;
- donut charts;
- таблицы топов;
- drill-down до заказов;
- IndexedDB для sales / purchases / finance;
- комиссию разделов;
- цену покупателю;
- точный расчёт цены;
- массовую работу с лотами.

Проблема UX: аналитика живёт на разных страницах FunPay и воспринимается как набор внедрённых блоков, а не как единый продукт.

## 2. Новая информационная архитектура

В боковом меню должна появиться основная страница:

**Финансы**

Внутри неё — tabs/subtabs:

1. **Обзор**
2. **Продажи**
3. **Покупки**
4. **Прибыль**
5. **Потенциал**
6. **Операции**

Существующие:
- Копилки
- Калькулятор
- Валюты

остаются в финансовом разделе как инструменты и не обязаны сливаться в один экран на первом этапе.

## 3. Что переносим

Из существующих FunPay-страниц переносим визуальное представление, но не ломаем источники данных:

### Продажи
Источник:
- `FPTSalesDB`
- текущая логика `sales_modes.js`
- `sales_chart.js`
- `stats_drilldown.js`

### Покупки
Источник:
- `FPTPurchasesDB`

### Операции

Сначала новые страницы должны переиспользовать агрегаторы и data access, а старые внедрённые отчёты продолжают работать как fallback. Их отключение — только TASK-10.

## 4. Новые сущности

### Cost Basis
Себестоимость единицы товара, задаваемая продавцом.

Хранится отдельно от FunPay.
Никогда не отправляется в native FunPay form.

Минимальная модель:
- `offerId`
- `nodeId`
- `amount`
- `currency`
- `updatedAt`
- `source`

### Profit Snapshot
Для новых заказов желательно фиксировать snapshot себестоимости на момент продажи, чтобы изменение себестоимости лота завтра не переписывало прибыль вчерашнего заказа.

Поля:
- `costBasisAmount`
- `costBasisCurrency`
- `costBasisCapturedAt`
- `offerId` (только если достоверно найден)

Не угадывать `offerId` по названию.

## 5. Новые метрики

### Потенциальный оборот покупателей
`buyerPrice * activeStock`

### Потенциальная выручка продавца
`nativeSellerPrice * activeStock`

В текущей архитектуре `buyer_price_field.js` считает buyer price из native FunPay price через multiplier. Поэтому нужно различать эти два значения в UI.

### Стоимость активного склада
`costBasis * activeStock`

Только по лотам, где себестоимость известна.

### Потенциальная чистая прибыль
`(nativeSellerPrice - costBasis - extraUnitExpense) * activeStock`

`extraUnitExpense` на первом этапе можно оставить 0 и предусмотреть в модели как будущее расширение.

### Реализованная чистая прибыль
`realizedSellerRevenue - capturedCostBasis`

Считать только по заказам с достоверной себестоимостью.
Неизвестная себестоимость != 0.

### Margin
`profit / sellerRevenue * 100`

### ROI
`profit / costBasis * 100`

## 6. Поведение при неизвестной себестоимости

Если часть данных не заполнена:
- не подставлять 0;
- показывать `—`;
- исключать такие заказы из суммы чистой прибыли;
- рядом показывать coverage:
  `Себестоимость известна для 72% оборота / 64% заказов`.

Это обязательно, иначе отчёт будет выдавать завышенную прибыль.
